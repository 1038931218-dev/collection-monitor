# 二、P0-01 我做了什么（已验收）

## 2.1 根因（两轮修复都漏掉的那一处）

| 文件 | 行 | 原代码 | 问题 |
|---|---|---|---|
| `src/file-parser/index.ts` | 219 | `return DateUtils.parseDate(String(value))` | **文件入口用宽松解析器** |
| `src/lib/decimal.ts` | 100 | `const date = new Date(str);` | **JS 自动滚动就发生在这里** |

`new Date("2026-02-30")` 会**静默返回 2026-03-02**，而不是报错。

第 2 轮只把 `analyze/route.ts`（API 入口）改用了 `StrictDate`，**文件入口没动** —— 这就是 R2-01。

## 2.2 四处修改

**① `src/file-parser/index.ts`**
- 日期解析从 `DateUtils.parseDate(String(value))` 改为 **`StrictDate.parse(value)`**
- **传原始值而非 `String(value)`**：Excel 未启用 `cellDates` 时日期是序列号数字，转成字符串会丢语义（`"46000"` 不是日期）
- 新增 `validateDates()`，**CSV 与 Excel 两个入口共用同一套校验**（防「修一个入口、漏另一个」复发）
- Excel 路径从 `.map()` 改 `for` 循环，以支持丢弃非法行

**② `src/data-normalizer/index.ts`**
- 严格区分「缺失」与「非法」：
  - `undefined`（源数据未提供）→ **保留既有行为**（保留发票 + `days_overdue=0`）
  - `null` / Invalid Date（提供了但解析不出）→ **拒绝，不进财务计算**
- ⚠ 这里我一度搞错：把「缺失」也当非法拒绝，**打破 7 个测试套件**。是 `[真脏-5]`/`[真脏-8]` 两个测试纠正了我 —— 它们锁定了「缺失 → 保留 + 未逾期」这条既有产品决策。

**③ `src/lib/decimal.ts`**
- `DateUtils.parseDate` 标记 `@deprecated`，**内部完全委托给 `StrictDate`**，堵死未来调用者重新引入宽松解析

**④ `src/lib/strict-date.ts`** —— **我攻击时发现的新漏洞**

原有 ISO 分支只做 `isNaN` 检查，**没有日历回环校验**：

```typescript
// 修复前
const iso = str.match(/^\d{4}-\d{2}-\d{2}T/);
if (iso) {
  const d = new Date(str);
  return isNaN(d.getTime()) ? null : d;   // ← "2026-02-30T00:00:00Z" 照样滚成 2026-03-02
}
```

**实测证据**：

```
[证据] 文件路径 "2026-02-30T00:00:00Z" → normalized.length=1
        due_date=2026-03-02  days_overdue=212
```

**而且 `StrictDate` 是 API 与文件两条入口共用的** —— 这个漏洞**同时打穿两边**。润策的派工单里没有这个变体，是我攻击时自己挖出来的。已修复并加为常驻攻击用例。
